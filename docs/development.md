## 1. チームと担当

全員学生の授業プロジェクトで、経験差があり、全員がAIによるコード生成を利用する可能性がある。

| メンバー | 主な担当 | 境界・連携 |
|---|---|---|
| **boo_manKnow** | リーダー。全体調整、データ契約・API・DB・認証、クラウド設定、リリース、レビュー | チーム内でWeb制作・プログラミング経験が最も多い。画面に必要な項目・操作は各担当と相談し、UIの細部は原則任せる |
| **yua** | 投稿一覧・カード・作成/編集・画像・検索/いいねUI | React/JS制作経験は少しある。ピンのフロント側取得・保持の主担当にする案。API/DBはboo_manKnowと合意し、地図描画はozako |
| **ozako** | UI統一、shadcn/ui・共通テーマ・サイドバー・レイアウト、Google Mapsと地図操作 | React/JS制作経験あり。共通デザインを管理するが全画面を作るわけではない。投稿データ取得の重複を避ける |
| **ha** | 旅行計画の一覧・詳細・作成編集UI、並び替え・時間入力 | React/JSによるサイト制作経験なし。データモデル・公開条件はboo_manKnowと確認し、地図連携はozakoと協働 |

## 2. GitHub運用

```text
feat/* → Pull Request → dev → Pull Request → main
```

- `main`: 安定版・本番反映元。
- `dev`: 開発統合ブランチ。
- `feat/*`: 各機能の作業ブランチ。
- featからdevへのPR作成は各実装者。マージは原則boo_manKnow。
- コンフリクトは原則PR作成者が解消。
- 直接push制限のGitHub設定は導入推奨（暫定）。

## 3. 実装順序

1. 各担当とデータ項目を協議し、共通の型・API契約とテーマ・基本UIを先に準備する。地図の外形や操作境界も試作する。
2. DBモデル・API入出力の型をレビューする。
3. `public/data` 等のモックを共通APIクライアント経由で利用し、並行開発する。
4. D1接続・テストAPI・認証・投稿APIを実装。
5. ピン投稿・閲覧の動作を完成。
6. 旅行計画の編集・公開・参照管理を実装。
7. いいね・検索・通報・画像削除等を統合。
8. デプロイと動作確認

Googleログインをどの時点で組み込むかは未決定。認可を伴うAPIの前に認証の基盤を用意するのが暫定提案。

## 5. テスト

詳細な自動テスト基盤は作らず、基本的に動作確認を優先する方針。ただし最低限、以下を確認する（暫定チェック項目）。

- 未ログインでの公開閲覧と書き込み拒否。
- 他人の下書き閲覧・編集の拒否。
- ピンの下書き→公開、公開→下書き拒否。
- 下書きピン入り計画の公開拒否。
- 公開計画への下書きピン追加拒否。
- 投稿削除後の計画内欠損表示。
- 画像3枚・5MB制限、削除時のR2消去。
- 退会時の関連データ削除。
- 同時アクセス時の主要画面の表示。
