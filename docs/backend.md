# バックエンド仕様

[目次へ](../README.md) · [DB](./database.md) · [API](./api.md) · [認証](./authentication.md)

## 1. 責務

Cloudflare上のサーバー処理で、認証、認可、D1の読み書き、R2画像操作、入力検証、公開条件判定、いいね、通報を担当する。実行環境はWorkersとPages Functionsのいずれかを決定する必要がある。

## 2. 共通原則（暫定設計）

1. 公開読み取りは認証不要。下書きは所有者にだけ返す。
2. 書き込み前にアプリセッションを検証し、所有者権限を確認する。
3. `user_id` はクライアントから信用せず、認証済みセッションから決定する。
4. DBクエリはパラメータ化する。
5. 投稿・計画の公開状態はサーバー側で判定する。
6. 画像処理はファイルの実体・形式・容量をサーバーでも検証する。
7. 参照整合性はD1外部キーとアプリ処理の両方で保つ。

## 3. ピンの状態遷移

```text
draft ──publish──> published
  │                    │
  └────delete──────────┴──> deleted（物理削除）
```

- `published → draft` は禁止。
- `draft → published` は必須項目の検証後に実施。
- 公開済みピンの更新・削除は所有者のみ。
- 削除時は関連する画像も削除する。参照している計画側には欠損プレースホルダーを残す。

## 4. 計画の公開処理

**確定**: 下書きピンが1件でも含まれていれば公開不可。公開済み計画への下書きピン追加は禁止。

**暫定実装手順**:
1. 認証・計画所有者確認。
2. 計画内のピン項目について、参照先が存在する全ピンの公開状態を確認。ひとコマはピンの公開状態確認の対象外。
3. 未公開ピンがあれば `409 CONFLICT` で拒否。
4. 条件を満たした場合のみ `plans.status` を `published` に更新。
5. チェックと更新の競合を避けるため、同一DB処理として整合性を確保する。

公開済み計画を下書きへ戻せるかは未決定。

## 5. 参照ピンの削除

- `plan_items` に独立した主キーと項目種別を持たせる案。
- `pins` 削除時にピン項目の `plan_items.pin_id` をNULLへ設定し、種別・順序・時間データを維持する案。ひとコマとは種別で区別する。
- APIでは `pin: null` を返し、フロントで「ピンが見つかりません」を表示する。
- 計画所有者がプレースホルダーを削除できる。
- **未決定**: 削除済みピンを含む公開計画の公開状態と、再設定操作。

## 6. アカウント削除

**確定**: 所有するピン、計画、画像、アカウントを削除。匿名投稿者としては残さない。

**暫定**: 退会処理で新規書き込みを停止し、関連レコードを整合的に削除した後、R2オブジェクト削除を行う。DBとR2に跨る単一トランザクションは存在しないため、途中失敗を検出・再実行可能にする。退会したユーザーのピンを参照していた他人の計画は欠損表示にする。

## 7. キャッシュ

**確定方針**: 公開投稿の読み取りに約1分のキャッシュを想定。**暫定**: 公開GETに `Cache-Control` を適用し、認証付きレスポンスや下書きは共有キャッシュ対象外とする。新規公開や削除後に最大約1分の表示遅延があり得ることを許容するかは最終確認が必要。

## 8. 管理処理

通報記録をD1へ保存し、運営者が確認して手動削除する。管理画面・通知方法・管理者認証方式は未決定。少なくとも一般利用者が管理APIを呼べない設計にする。
